## 1. Анализ производительности

### Горячие операции (hot paths)
Наиболее частые операции чтения в таком сервисе:
1. `GET /api/v1/recipes` — общий список рецептов и поиск по названию.
2. `GET /api/v1/recipes/{recipe_id}/ingredients` — чтение состава рецепта.
3. `GET /api/v1/users/by-login` — поиск пользователя по логину.
4. `GET /api/v1/users/search` — поиск пользователей по маске.
5. `GET /api/v1/users/me/recipes` — список собственных рецептов пользователя.
6. `GET /api/v1/users/me/favorites` — избранные рецепты.

### Потенциально медленные операции
Наиболее дорогие места по времени:
- запросы к PostgreSQL с `JOIN` и `GROUP BY` (`recipes + ingredients`, `favorites + recipes + ingredients`);
- текстовый поиск через `LIKE '%...%'`;
- проверка токена при авторизованных запросах;
- повторные одинаковые чтения одних и тех же данных.

## 2. Стратегия кеширования

### Выбранный подход
Использован **Cache-Aside (Lazy Loading)**:
1. handler сначала проверяет кэш;
2. если значения нет — читает из PostgreSQL;
3. сериализует ответ и кладёт его в in-memory cache с TTL.

Этот подход хорошо подходит, потому что:
- кэшируются только реально востребованные данные;
- можно тонко контролировать TTL для разных endpoint;
- запись в БД остаётся источником истины, а кэш — производным слоем.

### Что кешируется

#### 1) Поиск пользователя по логину
**Endpoint:** `GET /api/v1/users/by-login`
- Тип данных: редко меняющиеся пользовательские данные.
- TTL: **300 секунд**.
- Причина: профиль пользователя меняется редко, запрос часто повторяется.
- Ключ: `users:by-login:{login}`

#### 2) Поиск пользователя по маске
**Endpoint:** `GET /api/v1/users/search`
- Тип данных: результат текстового поиска.
- TTL: **300 секунд**.
- Причина: поиск по `LIKE` дороже простого точечного чтения.
- Ключ: `users:search:{mask}`

#### 3) Список рецептов / поиск рецептов по названию
**Endpoint:** `GET /api/v1/recipes`
- Тип данных: часто читаемые агрегированные данные.
- TTL: **30 секунд**.
- Причина: список рецептов читается часто, но изменяется заметно чаще, чем профили пользователей.
- Ключи:
  - `recipes:list:all`
  - `recipes:list:title:{title}`

#### 4) Ингредиенты рецепта
**Endpoint:** `GET /api/v1/recipes/{recipe_id}/ingredients`
- Тип данных: состав конкретного рецепта.
- TTL: **60 секунд**.
- Причина: запрос читается часто, а меняется только при добавлении ингредиентов.
- Ключ: `recipes:ingredients:{recipe_id}`

#### 5) Рецепты текущего пользователя
**Endpoint:** `GET /api/v1/users/me/recipes`
- TTL: **30 секунд**.
- Ключ: `recipes:user:{user_id}`

#### 6) Избранные рецепты пользователя
**Endpoint:** `GET /api/v1/users/me/favorites`
- TTL: **30 секунд**.
- Ключ: `recipes:favorites:{user_id}`

### Стратегия инвалидации
Используется **явная инвалидация** при операциях записи.

#### После `POST /api/v1/auth/register`
Инвалидируются:
- `users:by-login:{login}`
- все ключи с префиксом `users:search:`

#### После `POST /api/v1/recipes`
Инвалидируются:
- все ключи `recipes:list:*`
- `recipes:user:{author_id}`

#### После `POST /api/v1/recipes/{recipe_id}/ingredients`
Инвалидируются:
- все ключи `recipes:list:*`
- `recipes:ingredients:{recipe_id}`
- `recipes:user:{author_id}`
- все ключи `recipes:favorites:*`

#### После `POST /api/v1/users/me/favorites/{recipe_id}`
Инвалидируется:
- `recipes:favorites:{user_id}`

### Почему такая инвалидация подходит
- проще поддерживать корректность;
- меньше риск отдачи устаревших данных;
- меньше сложность кода.

## 3. Реализация кеширования

### Где кэш используется
- `GET /api/v1/users/by-login`
- `GET /api/v1/users/search`
- `GET /api/v1/recipes`
- `GET /api/v1/recipes/{recipe_id}/ingredients`
- `GET /api/v1/users/me/recipes`
- `GET /api/v1/users/me/favorites`

### Дополнительный признак для проверки
Для удобства ручной проверки в ответы добавлен заголовок:
- `X-Cache: MISS` — ответ получен из БД и сохранён в кэш;
- `X-Cache: HIT` — ответ отдан из кэша.

## 4. Проектирование rate limiting

### Реализованный endpoint
Реализован rate limiting для:
- `POST /api/v1/auth/login`

### Выбранный алгоритм
Использован **Fixed Window Counter**.

#### Почему именно он
- простая и понятная реализация;
- подходит для учебного REST API;
- хорошо работает для ограничения логина по короткому окну времени;
- дешёв по памяти и CPU.

### Настроенные лимиты
Для логина:
- **5 запросов в 60 секунд** на bucket.

Ключ bucket строится из логина и заголовка `X-Forwarded-For`:
- `rate-limit:login:{login}:ip:{forwarded_for}`

Это позволяет не блокировать всех пользователей сразу, а разделять попытки по логину/клиенту.

### Поведение при превышении лимита
Сервис возвращает:
- статус **429 Too Many Requests**;
- JSON-ответ с ошибкой;
- заголовки:
  - `X-RateLimit-Limit`
  - `X-RateLimit-Remaining`
  - `X-RateLimit-Reset`

---

## 5. Реализация rate limiting

В проект добавлен компонент `rate-limiter`:
- in-memory fixed-window counter;
- отдельные bucket по ключу;
- reset окна по времени;
- возврат решения `allowed / denied` и метаданных для заголовков.

Лимитер вызывается до обращения к PostgreSQL в `LoginHandler`, поэтому лишняя нагрузка на БД не создаётся.

---

## 6. Как кеширование и rate limiting улучшают производительность

### Эффект кеширования
Кеширование даёт:
- снижение числа одинаковых SELECT к PostgreSQL;
- уменьшение latency на горячих GET-операциях;
- уменьшение нагрузки на индексы, CPU и соединение с БД;
- лучшую устойчивость при всплесках чтения.

### Эффект rate limiting
Rate limiting даёт:
- защиту от brute-force на логине;
- снижение нагрузки на таблицы `users` и `auth_tokens`;
- защиту от резких всплесков однотипного трафика;
- более предсказуемое потребление ресурсов.
